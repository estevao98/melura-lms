# Data Inventory

This inventory maps the main personal data categories currently handled or
expected by the pedagogical LMS core. It does not invent database fields. When
the exact implementation detail is uncertain, it is marked as "to verify in
implementation".

The inventory should be revised whenever a DocType, whitelisted method, page,
integration payload, or external SaaS webhook changes.

| Category | Likely Source | Likely DocType / Service / Page | Purpose | Access Roles | LGPD Relevance | Risk Notes | Technical Controls Expected |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Student account data | Frappe `User`, LMS enrollment records, operational admin entry, future external SaaS reference resolution | Frappe `User`; LMS `LMS Enrollment`; LMS `LMS Batch Enrollment`; used by `zuno_lms.services.student_access` and `zuno_lms.services.whatsapp` | Authenticate students, display names, contact students for operational class notices, relate LMS access to a natural person | Student for own account through platform flows; Professor/admin only when needed for pedagogical operation; System Manager for technical maintenance | Personal data, identifiers, contact data, transparency and access rights | Phone/name may be exposed in WhatsApp previews/logs; account data may come from external commercial flow in future | Use Frappe auth; do not return broad user records; return only needed display/contact fields; restrict logs; keep secrets outside user records |
| Student access status | Manual admin maintenance today; future protected external SaaS webhook | `Bruce Student Access`; `zuno_lms.services.student_access` | Control pedagogical access status, course/batch scope, access period, and opaque external reference | System Manager, Moderator, Batch Evaluator currently have DocType permissions; students are checked through backend methods, not direct DocType write | Personal data linked to education access and service status; purpose limitation and minimization | `external_reference` must stay opaque; `notes` can become excessive if operators paste commercial or sensitive details | Only `Ativo` unlocks content; derive student from backend; validate status and dates; do not store financial payloads, tokens, card data, or unnecessary commercial data |
| Course/batch scope | LMS course/batch configuration; manual access records; future access integration | `Bruce Student Access.course`; `Bruce Student Access.batch`; `Bruce Live Class.course/batch`; materials/questions/lists scope fields | Limit content to the allowed pedagogical scope | Student through scoped results only; Professor/admin through role-checked dashboards and DocType permissions | Personal data when linked to a student's educational path | Cross-course or cross-batch access is a primary privacy/security risk | Query only through active access records; use permission query conditions for student-readable DocTypes; do not trust frontend scope parameters |
| Live class participation/access data | Live class records, Jitsi room generation, page access | `Bruce Live Class`; `bruce-live-room`; `bruce-professor-dashboard`; `minha-aula`; `Bruce Live Class Notice Log` | Schedule classes, allow authorized entry, record operational events | Student only when active and in scope; instructor for own classes; operational/admin roles for operations; System Manager for maintenance | Personal data and educational participation metadata | Room name or meeting URL leakage may allow unauthorized room access if not backend-checked | Generate room names server-side; validate status and access before returning room context; keep external Jitsi URL as explicit fallback only |
| Educational material access | Teacher/admin publication; student dashboard requests | `Bruce Educational Material`; `minha-aula`; `zuno_lms.services.student_access` | Deliver published materials to active students in course/batch scope | Student for published `Aluno` visibility in scope; teacher/admin roles for creation/maintenance | Educational data; may reveal course participation and learning plan | Private file URLs and unpublished/internal materials must not be exposed to students | Require `Ativo` access; filter by published and visibility; use permission hooks; avoid returning fields beyond UI needs |
| ENEM questions and answers | Teacher/admin question bank; student exercise flows | `Bruce ENEM Question`; `Bruce ENEM Question Alternative`; `Bruce Exercise List`; `Bruce Exercise List Item`; `zuno_lms.services.student_access` | Provide published questions and alternatives; evaluate answers | Student for published questions/lists in scope; teacher/admin for bank maintenance | Educational content plus student response data when answered | Answer key and commented resolution must not leak in student question list before answer submission rules allow it | Student question payload omits `correct_option` and `commented_resolution`; lists and questions require published/scope filters |
| Student answers | Student answer submission from frontend; backend save method | `Bruce Student Answer`; `save_student_answer`; progress helpers | Store selected option, computed correctness, and answer timestamp for the logged student | Student can submit own answer through backend method; Batch Evaluator/Moderator/System Manager can read through permissions; progress manager roles can see summaries | Personal educational performance data; access, correction, retention, and portability planning | Frontend must not control `student_user` or correctness; cross-student answer reads are high risk | Set `student_user = frappe.session.user`; compute `is_correct` server-side from question key; ignore permissions only after access validation; restrict direct DocType permissions |
| Progress metrics | Derived from active access, exercise lists, and student answers | `get_progress_for_current_student`; `get_class_progress_summary`; dashboards | Show student progress and operational class progress | Student for own locked/unlocked progress; Professor/admin/progress manager roles for class summaries | Personal educational profiling/performance data | Blocked/expired/pending students must not receive protected progress metrics; aggregate dashboards can still expose individual inactive students | Return locked zero metrics for non-active access; protect class progress with manager roles; avoid excessive fields |
| WhatsApp notification metadata | Manual send/preview; class recipients from batch enrollment or manual phone | `Bruce WhatsApp Notification Log`; `Bruce WhatsApp Message Template`; `Bruce Evolution Settings`; `zuno_lms.services.whatsapp`; `Bruce Live Class Notice Log` | Prepare, preview, send, and audit operational class notices | Authorized class writers for preview/send; System Manager/Moderator for settings; Batch Evaluator read access to logs as currently configured | Contact data, communication metadata, possible consent/transparency relevance | Logs can contain phone, recipient name, message body, provider response; provider response must not contain tokens/secrets | Keep provider calls backend-side; redact sensitive response keys; do not return API key; store short errors; review retention for logs |
| Operational logs | Backend actions, notices, send attempts, framework logs | `Bruce Live Class Notice Log`; `Bruce WhatsApp Notification Log`; Frappe logs to verify | Support, audit, incident response, troubleshooting | System Manager, Moderator, Batch Evaluator where configured; operational admins through dashboards where implemented | Accountability, security, incident response, data minimization | Logs can become personal data dumps if full payloads or provider responses are stored | Log only needed context; redact secrets; preserve failure history; define retention and access boundaries |
| Future external SaaS opaque references | Future protected webhook from external financial/commercial SaaS | `Bruce Student Access.external_reference`; future service endpoint to verify in implementation | Correlate access status with external system without importing billing logic | Integration/bot user or protected endpoint; operational/admin review only as needed | Shared processing, controller/operator boundary, minimization, webhook risk | Webhook spoofing could activate access; external reference could become a hidden financial payload if misused | Verify webhook signature/secret; store only opaque reference and pedagogical status; idempotent updates; reject card/payment/full commercial payloads |
